## 分析：棋盘「HTML 画布」的实现本质（只做分析，未改代码）

用户问「现在使用的是 HTML 画布，优缺点是什么」。核查结论（可直接引用）：

- **全库 grep `<canvas` / `getContext` = 0。** 棋盘画布是 **DOM + CSS transform
  + SVG 复合体**，不是 Canvas API：滚动容器 div（overflow:auto，平移=原生滚动）
  → 尺寸层 div（board.width × zoom）→ 背景 `<img>` + scale(zoom) → 网格 SVG
  （GridLayer 注册表）→ 关系线 SVG（RelationLines 分组聚合）→ token = 绝对定位
  DOM，直接渲染 CardFrame React 组件 → 交互浮层（拖拽预览/框选/测量线）。
  DESIGN.md §3.3 表格里「HTML 画布」指的也是这个。
- **最大架构红利**：token 复用真实 CardFrame 组件，6+ 卡框风格/闪卡/卡背/立绘
  零成本上棋盘；hover/focus/a11y/主题 CSS 变量全是浏览器原生能力。
- **主要成本**：每 token 一棵完整 DOM 子树，无虚拟化（卡片墙有 240 张限额，
  棋盘没有）；拖拽时每帧移动 N 个绝对定位元素。
- **结论**：当前方案对「卡牌即内容」是对的选择；该做的是视口虚拟化 + 拖拽降级
  （参照卡片墙限额同源思路），不是换 canvas。真正需要 canvas 的理由只有一个：
  未来要「导出棋盘为图片」（DOM 方案只能靠 html2canvas 类库，装不上）。

## 分析：卡组功能优化（只做分析，未改代码，待用户选方向）

现状盘点（代码核查）：数据层 CardGroup = { name, description, card_ids 有序多重集 }；
编辑器（CardGroupEditor：名称/描述 + grid/list 双视图 dnd-kit 排序 + ×N 聚合 +
CardGroupPicker 搜索加牌 + 按类型填充追加/替换）；列表页（EntityListLayout +
新建二选一 + 引用感知删除）；消费方四个（卡片墙多选加入 AddToGroupDialog、
棋盘从卡组导入/加卡盒、会话 group_id 当队伍、资源包导出导入合并）。

优化机会分级（价值 × 成本）：
1. **组内检索 + 类型过滤缺失**（高价值低成本）：100+ 张的组只能滚找；
   picker 有搜索但组内列表没有，useCardWallFilters 的设施没复用过来。
2. **「用在哪」不可见**（中价值低成本）：删除时能看引用（piles/session），
   平时不可见；与 §4.9「核心不保护被引用状态」哲学互补的是让人看得见。
3. **P2 待办「卡组同步到棋盘（只补不删）」未实现**（高价值中成本）：
   卡组加新卡后棋盘上已铺的不更新。
4. **视图双实现 95% 重复**（低用户价值低成本）：grid.tsx / list.tsx 的
   DndContext/sensors/handleDragEnd 完全相同，只有 strategy 与行渲染不同。
5. **AddToGroupDialog 无搜索**（中低价值低成本）：卡组数通常 <20，优先级低。
6. 小项：×N 卡只能一份份移除；新建按类型生成时 GenerateByTypeDialog 的
   mode 参数被忽略（_mode 死参数）。
