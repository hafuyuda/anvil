## 0. 核心问题界定（先于盘点）

在砍功能之前，必须先回答「跑团模块为谁解决什么」。

### 0.1 现状定位：桌面战棋的骨架，装在叙事工具里

模块当前同时承担三件性质不同的事：

| 定位 | 载体 | 是否匹配 Anvil 的能力边界 |
|---|---|---|
| 叙事记录器 | 对话流 + 牌谱 | **匹配** —— 卡牌 + 事件的既有资产全部用得上 |
| 角色状态面板 | PartyPanel（数据活在卡上） | **匹配** —— §14.5 硬约束，不另建角色模型 |
| 战斗秩序管理 | 先攻追踪 | **不匹配** —— 完整战斗必然要命中判定、伤害、护甲，那是规则引擎 |

第三条已在 §14.4 被明确否认：「Anvil 记录『掷出 13』，不回答『13 对 DC 12 算不算成功』」。
**先攻追踪是这一边界被划出之后遗留的半截设计** —— 它保留了「轮到谁」的战棋骨架，却抽掉了让骨架产生意义的血肉。这是战斗功能体验薄弱的根因，不是表象。

### 0.2 更深一层的根因：协作模型缺失

Anvil 是单机 Tauri 应用。KP 全景 / 玩家视图是**同一台机器上的两个滤镜**，依赖 Ctrl+G 手动切换。

由此推出：所有「为玩家在场而设计」的设施，在真实使用中都缺少使用场景 ——

- 玩家视图：KP 得自己按键切换，玩家得凑到同一块屏幕前；
- 先攻条在玩家视图下的只读态：全部按钮 `disabled`，玩家看到的只是高亮 chip；
- 战斗的收益本应由「玩家知道自己何时行动」产生，而这个收益在当前形态下无法兑现。

> **待确认假设 A1**：战斗使用率低的深层原因是「协作模型缺失」而非「战斗做得不好」。
> 证实方法：若存在远程/分屏/多端能力，战斗与玩家视图的收益模型完全不同，本方案第 3 章的处置结论需整体重估。
> 仓库内无相关埋点、无样例项目数据（`events.jsonl` 数量为 0），无法用数据证实或证伪。

### 0.3 结论：模块真正要解决的问题

> **跑团模块 = 单人 KP 工作站的叙事记录器。**
> 它要解决的问题是：一局跑团结束后，能完整、可信、可回看、可导出地留下「发生了什么」。

在这个定位下：

- **有价值**：记录（对话流 / 骰点 / 棋盘步骤）、回看（牌谱回放）、产出（战报导出）；
- **无价值**：任何需要「玩家在场」才产生收益的设施，以及任何模仿桌面战棋的秩序管理。

战斗功能应**从「独立子系统」降级为「通用行动顺序工具」** —— 它不只服务战斗，还服务交涉、探索、追逐等任何需要「轮到谁」的场景。降级后使用面变宽，实现成本从 475 行降到约 80 行。

## 2. 战斗功能「鸡肋」的问题诊断

七条原因，按严重度排序。每条都附代码依据。

### 2.1 【最严重】战斗在叙事流里不可读 —— 与叙事脱节

`src/features/session/chat/ChatSystemLine.tsx:28-73` 的 `systemText` 分支列表为：
`session.start` / `session.end` / `token.move` / `board.step` / `state.set` / `effect.apply` / `note` / `default`。

**`combat.turn` 与 `combat.round` 不在其中**，落到 `default: return event.kind`。

后果：每次推进轮次，对话流里插入一行系统线，显示的是**英文 kind 原文**：

```
────────── combat.turn ────────
────────── combat.round ────────
```

这是对整个诊断最有力的一条证据：**战斗确实发生了（有状态、有事件、有 UI 控件），但它在叙事记录里留不下任何可读痕迹。** 用户事后回看对话流，看到的是一串英文标识符。战斗与叙事是两条互不相干的平行线。

### 2.2 战斗与角色数值是断裂的两条链路

战斗追踪只解决「轮到谁」，不解决「打得怎么样」。一次完整的攻击在当前形态下需要：

1. 在先攻条上点「下一个」；
2. 在对话流里掷 `1d20`（攻击）；
3. 在对话流里掷 `1d8`（伤害）；
4. **切到右侧 PartyPanel，对目标点 N 次「−」手工扣血**；
5. 切回先攻条点「下一个」。

第 4 步是关键：战斗系统与角色数值之间**没有任何数据流**。战斗产生的唯一效果是 `tracker.turn_index` 加一。

对照 §14.5「角色的一切数据都活在卡牌上」—— 战斗恰恰是唯一没有把数据写到卡上的环节。

### 2.3 入场成本过高，且高频操作没有回报

**入场 5 步**（`InitiativeDialog`）：

1. 打开对话框；
2. 逐个勾选参与者（候选者来自 `session.tokens` 上有卡的 token）；
3. 逐个点「掷」或逐个手填数值；
4. 逐个点 PC/NPC 按钮切换（候选者全部 `isPc: false`，见 `SessionEditor.tsx:228`，无默认值来源）；
5. 点「开始战斗」。

典型 5 人小队 + 4 敌人 = **9 次勾选 + 9 次掷骰 + 9 次阵营切换 = 27 次点击**，才换来一个「第 1 轮」。

**运行中**：每回合点「下一个」，触发 `savePatch`（一次 IPC 写会话）+ `logEvent`（一次 IPC 写事件），换来的回报是 chip 高亮右移一格 —— 而这格高亮在叙事流里还显示为 `combat.turn`。

### 2.4 先攻值没有数据来源，是硬编码裸骰

`InitiativeDialog.tsx:7`：

```ts
const INITIATIVE_EXPR = "1d20";
```

规则集在 0.4.0 移除后，先攻值不再与卡上任何字段关联。卡上可以有「敏捷 15」，先攻仍是纯 `1d20` 裸骰。

这是 0.4.0「删规则集」这一刀留下的**未愈合创面**：删掉了判定，却保留了依赖判定的秩序机制。§14.2 写「Anvil 不替用户推导 DEX 顺序或敏捷调整值」—— 这是主动选择，不是缺陷；但结果是先攻值变成了与角色无关的随机数，先攻序列丧失了「角色能力决定行动先后」这一唯一意义。

### 2.5 常驻 UI 与真实使用率严重不匹配

`InitiativeBar` 在 `SessionEditor` 中无条件渲染，`minHeight: 40`。非战斗态时它显示的内容是：「先攻」两个字 + 一个「开始战斗」按钮。

按投入产出比：40px 常驻空间 + 193 行代码，换取一个 90% 时间用不到的入口。

### 2.6 战斗历史本身是残缺的

| 操作 | 是否写入事件流 |
|---|---|
| `handleInitiativeApply`（开战） | 是 —— `combat.round` |
| `handleNext` | 是 —— `combat.turn` |
| `handlePrev` | **否** |
| `handleResetInitiative` | **否** |
| `handleEndCombat` | **否** |

连带后果：轮次从最后一人回绕到第一人时（`SessionEditor.tsx:377-380`），`round` 自增，但只记 `combat.turn`，**不再记 `combat.round`**。即「第 2 轮开始」这个节点在记录里不存在。

战斗结束也不留痕迹 —— 既无 `session.end` 意义上的结束标记，也无战斗摘要。

### 2.7 战斗态与棋盘脱节

`InitiativeEntry` 带 `token_id`，但推进轮次时：

- 棋盘上对应 token **不高亮、不居中**；
- 条上的 `turn_index` 与棋盘的 `selectedTokenId` 是两套互不相干的状态。

玩家（KP）推进了轮次，视线要从顶栏条 → 棋盘上自己找那个 token。这一步人工搜索在多人场面下是实际负担。

### 2.8 补充：战斗缺乏终局产出

战斗结束时 `handleEndCombat` 只把 `active` 置 false。没有战利品、没有经验、没有叙事摘要、没有伤亡统计。

一局 40 分钟的战斗，在 Anvil 里留下的全部痕迹是：若干行 `combat.turn` + 若干次手动 HP 改动 + 若干条掷骰消息。**它不产生任何「打完这一仗我得到了什么」的收益。**

## 3. 精简与调整方案

### 3.1 处置结论总表

图例：**保留** = 现状即合理；**改造增强** = 保留概念、重写实现或补缺失环节；**合并简化** = 保留能力、砍掉冗余入口；**删除** = 移除代码与 UI。

| # | 功能 | 处置 | 理由 | 删除/改造的影响与缓解 |
|---|---|---|---|---|
| A1 | 会话列表 | 保留 | 入口容器，复用通用布局，成本低 | — |
| A2 | 会话命名 | 保留 | 必要标识 | — |
| A3 | 四种排序 | **合并简化** | 会话数量通常个位数，排序是伪需求；保留「最近更新」一种即可 | 影响：极少数多会话项目失去创建序/名称序。缓解：保留默认排序，砍掉下拉 UI |
| B1 | 战场棋盘选择 | **改造增强** | 现状切换棋盘会清空本会话 tokens 并弹危险确认，是破坏性操作 | 影响：改为「追加选中 token」或「保留位置合并」后，切棋盘不再丢数据。需先确认用户是想要「换战场」还是「加桌子」 |
| B2 | BoardCanvas 舞台 | 保留 | 复用棋盘模块，零成本 | — |
| B3 | 卡盒抽牌 | 保留 | 遭遇堆/战利品，与卡牌体系契合 | — |
| B4 | 克隆 board tokens | 保留 | 会话持有副本是 §14.7 牌谱前提 | — |

### 3.2 战斗精简后的目标形态

**去掉「战斗」这个独立概念，保留并泛化为「行动顺序」。**

| 维度 | 现状 | 目标 |
|---|---|---|
| 名称 | 先攻 / 战斗 | 行动顺序 |
| 适用范围 | 仅战斗 | 战斗、交涉、探索、追逐 —— 任何需要「轮到谁」的场景 |
| 常驻形态 | 40px 条 + 1 个按钮 | 顶栏 90px 按钮 |
| 入场 | 5 步 27 次点击 | 1 次点击（默认全选 + 自动掷骰） |
| 入场配置 | 对话框 | 无对话框 |
| 运行按钮 | 前进/后退/重置/结束 | 前进/结束 |
| 阵营标记 | 逐人点击 | 卡类型继承或不标记 |
| 与棋盘 | 无联动 | 自动选中并居中 |
| 与叙事流 | 显示 `combat.turn` | 显示「第 2 轮 · 索林行动」 |
| 代码量 | 475 行 | 约 80 行（−83%） |

**kind 名保持 `combat.round` / `combat.turn` 不变** —— 遵循 §14.1「纯增字段、向后兼容不迁移」的既有原则，改名会破坏已落盘的事件流。

### 3.3 最小可用范围（MVP 边界）

精简后，跑团模块的最小可用范围由三件构成，其余全部是可选增量：

```
MVP = 记录（对话流 + 骰点）  ⊕  角色（卡即角色）  ⊕  回看（牌谱）
                          ↑ 贯穿层：KP / 玩家 双层视图
```

**边界规则（写进 DESIGN.md，作为后续需求的第一道闸门）：**

1. **不判定**：不引入任何规则集、目标值、成败标签。掷骰只记录点数。
2. **不做协同**：不引入多端、分屏、实时同步。视图是滤镜，不是协作。
3. **不另建角色模型**：角色数值一律读写卡牌字段，会话内不存角色副本。
4. **行动顺序只管秩序**：记录「轮到谁」，不管「打得怎么样」。后果由 KP 落到卡牌上。

任何新需求先过这四条，过不了就不进模块。

### 关于「强化掷骰判定」的正面回应

用户第 4 点提到了「掷骰判定」。这里必须明确：**建议强化的是「掷骰 → 后果」的闭环，不是判定本身。**

- 判定（「13 对 DC 12 算不算成功」）要读卡、读状态、读武器护甲，是规则引擎，§14.4 已划出边界，**不应回头**；
- 但「掷出 1d8 = 6，把这 6 点扣到哥布林身上」不是判定，是**把 KP 的既有决定落到数据上**。

N2 做的正是后者。它让掷骰从「记下一个数字」变成「改变了世界状态」，且不触碰边界。

## 5. 落地顺序

### 阶段 0 · 定边界（不改代码，先落文档）

| 项 | 内容 | 产出 |
|---|---|---|

**验收**：新建会话 → 开战 → 推进三轮，对话流里读到「第 2 轮开始」「第 2 轮 · 索林行动（先攻 17）」，无英文 kind 残留。

1. 删 `InitiativeDialog.tsx`（222 行）与 `InitiativeBar.tsx` 的常驻形态；

5. 推进轮次时自动选中并居中棋盘上对应 token。

**验收**：开序从 27 次点击降到 1 次；非战斗态顶栏不占整行；战斗相关代码 ≤ 100 行。

### 阶段 3 · 闭环：让掷骰产生后果（P0-N2）

1. 掷骰消息上增加「应用到…」动作，弹出目标选择（场上角色）；
2. 选定后把点数写入目标卡的 HP（扣血）或指定字段；
3. 落一条系统事件记录这次应用，使它在流与记录里可追溯。

**验收**：掷 `1d8` → 得 6 → 应用到哥布林 → 哥布林 HP 条下降 6 且在对话流留痕。全程无命中判定。

### 阶段 4 · 增强：记录兑现为产出（P1）

1. N4 会话章节标记 + 跳转；
2. N5 战报导出（Markdown）；
3. N6 角色视角（**先做 N6 的数据结构评估，评估不通过则降级为 P2 或直接砍**）。

**验收**：一局会话结束后能一键导出一份含旁白、对白、骰点、牌谱摘要的 Markdown 战报。

### 阶段 5 · 收敛

1. A3 排序简化、E10 BGM 按钮处置；
2. N7 / N8 按阶段 4 的验证结果决定；
3. 同步 `docs/DESIGN.md` §14 全部小节与 §24 待办清单；
4. 回归：牌谱回放、撤销/重做、秘密/揭示三条链路不受影响。

### 阶段间的取舍原则

- 阶段 1 可以独立于阶段 2 先上 —— 它是纯修复，风险最低，收益立竿见影；
