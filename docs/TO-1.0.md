## 2. 优先级清单（高 → 低）

排序原则：**正确性 / 数据安全 > 可用性 > 规模化 > 文档与预期对齐 > 模型收敛**。
1.0 是稳定版，不是功能完备版。

### P0 — 数据安全与崩溃（阻塞 1.0）

**P0-1　建立「外来 id / 路径先校验再落盘」的纵向防线**

- 类别：缺陷修复（安全）
- 内容：① `cards.rs:9` 改用字符边界安全的分片（或直接放宽为不切片）；
  ② 统一实体 id 合法性校验函数，所有 `*_path()` 与导入落盘前调用；
  ③ `pack.rs:183` 补全 zip-slip 防护（canonicalize 后校验前缀，与 `preset.rs` 统一）。
- 预期收益：消除「导入一个别人给的资源包 → 进程崩溃 + 项目外任意写」这整类问题。
  这是目前**唯一能造成不可恢复损坏**的缺陷类别。
- 工作量：**中**（改动点分散在 7 个 store 文件 + pack/preset，但每处很小）
- 风险与依赖：需先定死「合法 id」规则并与现有 uuid 兼容（现有 id 全是 uuid，
  收紧不会误伤）；导入路径校验若过严会拒掉历史包。建议配一组回归用例锁住行为。
- 排序理由：`release` 是 `panic = "abort"`，任何一次 panic 都是**硬退出而非一条
  toast**，且可能正卡在写盘中间。其余所有改进都建立在这个不崩的前提上。

**P0-2　修「清理未引用图片」的误删**

- 类别：缺陷修复
- 内容：`find_unused_images` 补上棋盘 `board.background` 与剧本 `@bg` 两类引用源。
- 预期收益：避免一键删除在用资源。删除**不可逆、无备份**。
- 工作量：**小**
- 风险与依赖：统计口径变宽 = 判定更保守，只会少删不会多删，无向后兼容风险。
- 排序理由：收益/成本比最高的一条。一个 20 行的改动挡住不可逆数据丢失。

**P0-3　剧本保存失败必须让用户知道**

- 类别：缺陷修复
- 内容：`flushAll` 失败时保留脏标记、给 toast、提供重试；不要无条件 `setDirtyFiles({})`。
- 预期收益：不再静默丢稿，界面不再谎报「已保存」。
- 工作量：**小**
- 风险与依赖：需设计失败态 UI（脏标记保留 → 顶部提示 → 重试按钮）。
- 排序理由：创作工具丢用户稿子是最严重的信任损失，且当前行为是**界面主动误导**，
  比单纯的功能缺失更糟。

### P1 — 一致性与回归护栏（阻塞 1.0）

**P1-1　单实例 / 项目文件锁**

- 类别：功能补全 + 缺陷修复
- 内容：打开项目时加锁文件，第二个实例拒绝或只读；异常退出后能识别并清理陈旧锁。
- 预期收益：消除双实例互相静默覆盖（后写覆盖前写，用户零感知）。
- 工作量：**中**
- 风险与依赖：锁残留处理要小心（崩溃后遗留锁不能把用户永久挡在门外）；
  与外部编辑器同时改文件的交互需要明确语义。
- 排序理由：与 P0 同属「静默数据丢失」，但触发条件更窄（需用户主动开两个实例），
  故排在 P0 之后。

**P1-2　给 pack.rs 与 index/mod.rs 补测试**

- 类别：测试
- 内容：pack 导出 / 导入 / 合并往返、`TypeMapAction` 三分支、路径遍历守卫（专项
  安全用例）、`sanitize_fts_query` 转义、索引级联删除与 rebuild 事务。
- 预期收益：锁住数据迁移与全文检索这两条**最容易静默出错**的路径；安全边界有回归保护。
- 工作量：**大**（pack 需构造 zip 夹具）
- 风险与依赖：夹具构造是一次性投入；无 jsdom 不影响（纯 Rust）。
  建议先补 index（小），再攻 pack。
- 排序理由：1.0 的「稳定」需要**可回归**来证明。这两块恰好是 0 覆盖 + 高风险的交集。

**P1-3　损坏实体不要静默消失**

- 类别：缺陷修复
- 内容：解析失败时不要 `eprintln` 后跳过，改为收集到「问题实体」列表并在 UI 呈现；
  `rebuild` 前先备份索引（或改成非破坏性重建）。
- 预期收益：从「搜不到、不知道为什么」变成「知道哪里坏了」。
- 工作量：**中**
- 风险与依赖：需设计损坏实体的呈现方式（隔离区 vs 报错列表）；改 `rebuild` 语义
  有数据风险，务必先有 P1-2 的测试。
- 排序理由：静默丢失是信任杀手；`rebuild` 的全删重建会把「看不见」升级成「真没了」。

### P2 — 可用性与规模化

**P2-1　去掉「窗口获得焦点就全量重载」**

- 类别：性能
- 内容：`AppShell.tsx:72-103` 在 focus（500ms 防抖）后调 `reloadProject()`，
  后端 `reload()` **从磁盘全量重读所有实体**（卡 / 类型 / 关系 / 剧情 / 棋盘 / 会话 /
  卡组 / 文档）并整个替换前端 store。改为脏检测（mtime 或版本号）+ 增量同步。
- 预期收益：重度项目下 alt-tab 切回来不再秒级卡顿。这是目前**唯一必现**的大规模卡顿。
- 工作量：**中**
- 风险与依赖：改错会导致外部修改不同步 —— 必须保留「检测到外部变更时全量重载」的
  兜底路径。建议先加埋点确认真实开销，再动手。
- 排序理由：每次切窗必现，重度用户无法忍受；且它同时拖慢「删除 → reloadIntoStore」
  这一整条高频路径。
- 更正说明：调研初报称此处会「全量重建 SQLite 索引」，**经核实不准确** ——
  `reload()` 不碰索引（索引重建只在 `open` 时按 `needs_rebuild` 触发）。
  实际开销是全量读盘 + 全量替换 store，仍然显著，但量级低于初报。

**P2-2　图片缩略图**

- 类别：性能 + 功能补全（ROADMAP 既有条目）
- 内容：导入 / 首次访问时生成缩略图并缓存，卡片墙与文档库用缩略图而非原图。
- 预期收益：卡片墙 240 张原图 → 内存占用与首屏时间大幅下降。
- 工作量：**中**
- 风险与依赖：需引入 Rust `image` crate（**本机沙箱拉不了 crates.io，需在有网环境做**）；
  缩略图失效与重建策略需设计。
- 排序理由：与 P2-1 同为规模化阻塞项，但触发频率低一档（只在资源多的项目）。

**P2-3　批量删除合并为一次扫描**

- 类别：性能
- 内容：`CardWall.tsx:160-162` 循环调 `ipc.deleteCard`，每次触发
  `refs.rs` 全量 load_boards + list_all_relations。改为后端批量接口。
- 预期收益：删 100 张从 100 次全项目读盘降到 1 次。
- 工作量：**小-中**
- 风险与依赖：`refs.rs` 需支持批量入参。
- 排序理由：常见操作，规模放大明显，改动不大。

**P2-4　文档库与棋盘缩略图加限额 / 虚拟化**

- 类别：性能
- 内容：`DocLibrary.tsx:78-87` 全量 `visibleCards.map`（5000 卡一次挂载）；
  `BoardThumbnail.tsx:30-49` 每盘全量画 token（50 盘 × 300 = 15000 SVG 节点）。
- 预期收益：避免打开即假死。
- 工作量：**小**
- 风险与依赖：低。与项目既有「先限额再动效」原则一致。

## 3. 本排序所依据的假设

1. **1.0 = 稳定版，不是功能完备版。** 优先正确性、数据安全、可回归，
   不追求补齐所有已设计但未实现的模型字段。若你的 1.0 定义是「功能齐全」，
   P4 应整体上调，P0/P1 的紧迫性不变但相对权重下降。
2. **延续 DESIGN §24 的边界**：单人、本地、无联机、无规则引擎。
   本报告未按「多人协同」方向考虑任何事项。
3. **重度项目规模假设为 5000 卡 / 50 棋盘（每盘 300 token）/ 200 剧情文件 /
   5000 条事件的会话。** P2 的全部性能项都建立在这个量级上。
   若真实用户的项目规模小一个数量级，P2 应整体下调到 P3 之后。
4. **没有任何真实用户反馈数据。** 缺陷的严重度是静态分析得出的「后果 × 可达性」，
   不是实际发生频率。真实反馈很可能重排 P1/P2 的内部顺序。
5. **0.4.0 刚发布，假设 1.0 之前不再做破坏性数据格式变更**（schema 保持 0.4）。
   若允许再破一次，P4 的死字段清理可以做得更彻底（直接删字段而非软兼容）。
6. **Rust 依赖可以联网获取。** 沙箱环境拉不了 crates.io，P2-2 的 `image` crate
   需在有网环境引入。若不能引入新依赖，P2-2 需换方案（如前端 canvas 降采样）。
7. **投入节奏偏小步：** 按「最小可交付」估工作量，每条都拆到能独立合入。
